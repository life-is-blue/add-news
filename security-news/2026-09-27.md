## 1. 两项恶意GitHub Actions被重新启用，旧供应链攻击复活【72小时扩展】

- **分类**：软件供应链、GitHub Actions、CI/CD凭据风险
- **严重度**：严重
- **发布日期**：2026-09-24至26
- **可信度**：初步披露（Socket原始技术研究、公开工作流运行证据；GitHub尚未公开解释重新启用原因）
- **影响对象**：在工作流中以标签引用 `actions-cool/issues-helper` 或 `actions-cool/maintain-one-comment` 的GitHub仓库，尤其是9月16日至25日期间运行过相关Action的项目
- **发生了什么**：这两项Action在5月Mini Shai-Hulud攻击中被植入窃密代码并由GitHub封禁。9月16日，它们在恶意release标签未被清理的情况下重新可访问，导致使用 `@v2.2.1` 等可变标签的下游工作流再次下载并执行旧载荷。Socket从运行日志确认，runner解析到含混淆载荷的提交，并安装Bun执行 `index.js`。GitHub依赖图显示仅 `issues-helper` 就约有1.5万个依赖仓库，但实际使用受影响标签并运行过的数量尚未确定。两仓库已于9月25日再次被禁用。
- **为什么值得关注**：攻击者没有重新入侵或发布新版本，仅靠平台恢复访问就重新激活了数月前的恶意供应链。它揭示了“封禁仓库”只是临时隔离，而可变标签会让下游代码在工作流未发生任何变更的情况下改变；这类Action还能读取 `GITHUB_TOKEN` 和工作流显式提供的机密。
- **建议行动**：
  1. 全组织搜索 `.github/workflows/` 中的 `actions-cool/issues-helper@` 和 `actions-cool/maintain-one-comment@`，立即移除。
  2. 对9月16日后运行过相关工作流的仓库，轮换工作流可访问的全部机密，并审查 `GITHUB_TOKEN` 权限和异常提交。
  3. 在日志中查找 `oven-sh/setup-bun`、`bun run $GITHUB_ACTION_PATH/index.js`，以及由数秒失败突然变成长时间成功的运行。
  4. 所有第三方Action改用经核验的完整commit SHA；同时限制默认令牌权限，并避免向问题/评论触发的工作流暴露高价值凭据。

## 2. ShinyHunters绕过PeopleSoft WAF规则，恢复大规模利用

- **分类**：在野漏洞、企业应用、数据窃取与勒索
- **严重度**：严重（CVE-2026-35273，未经认证远程代码执行）
- **发布日期**：2026-09-25至26
- **可信度**：多方确认（Mandiant与Google威胁情报团队原始调查；Oracle已发布补丁）
- **影响对象**：未修补Oracle PeopleSoft、仅依赖WAF封锁 `/PSEMHUB/` 的组织；受害行业包括高等教育、科技、IT服务、医疗、农业、交通和政府
- **发生了什么**：Mandiant确认UNC6240（ShinyHunters）恢复对PeopleSoft CVE-2026-35273的大规模利用。攻击者把请求路径从 `/PSEMHUB/` 改为 `/%50SEMHUB/`，用字符P的URL编码绕过按原始字符串匹配的WAF规则；PeopleSoft后端解码后仍把请求送达漏洞端点。研究人员在全球数十套系统观察到Web Shell部署，也发现不落地文件的命令执行，意味着只监测JSP文件不足以发现攻击。
- **为什么值得关注**：这是“缓解措施被适配”的典型案例。组织若把WAF路径封锁误当成补丁，可能在仪表盘显示已阻断的同时继续被利用。PeopleSoft通常连接人事、财务、学生或政府业务数据，Web层失陷还可通过应用服务账户扩展到数据库、Integration Broker和云环境。
- **建议行动**：
  1. 立即安装Oracle针对CVE-2026-35273的安全更新；WAF规则不能替代修补。
  2. 按Oracle指引禁用EMHub服务或移除PSEMHUB应用，并让WAF在规范化、URL解码后的路径上执行策略。
  3. 搜索 `/%50SEMHUB/hub` 及其他编码、混合大小写变体，检查所有负载均衡节点中的 `x.jsp`、`u.jsp`、`tunnel.jsp[x]` 和未知JSP。
  4. 检测WebLogic Java进程派生 `cmd.exe` 或 `/bin/sh` 的行为，并轮换PeopleSoft服务账户可读取的数据库、Integration Broker及云凭据。
- **原始来源与补充来源**：
  - [Google Cloud/Mandiant：ShinyHunters恢复大规模PeopleSoft利用](https://cloud.google.com/blog/topics/threat-intelligence/shinyhunters-renewed-mass-exploitation-campaign-targeting-oracle-peoplesoft)
  - [Oracle：CVE-2026-35273安全警报](https://www.oracle.com/security-alerts/)
  - [BleepingComputer：URL编码绕过WAF的攻击更新](https://www.bleepingcomputer.com/news/security/shinyhunters-uses-waf-bypass-trick-in-oracle-peoplesoft-attacks/)

## 3. Bitget公布提款恢复计划，完整根因仍待发布

- **分类**：重大资产盗窃、事件响应与恢复
- **严重度**：严重
- **发布日期**：2026-09-26至27（对昨日事件的实质后续）
- **可信度**：官方确认（Bitget公告；Mandiant与SlowMist继续参与调查）
- **影响对象**：Bitget交易所用户、提款系统和支持的多条区块链网络
- **发生了什么**：Bitget称导致约3.875亿美元资产转移的漏洞已经识别并修复，事件保持受控，没有新的未授权转账。平台公布分阶段恢复提款计划：9月28日恢复BTC，9月29日恢复ETH及多个EVM网络，9月30日恢复USDT，其他代币、法币和P2P计划在10月2日恢复。公司称保护基金覆盖财务影响，但尚未发布承诺中的完整根因和控制失效细节。
- **为什么值得关注**：提款恢复说明事件从遏制进入业务恢复阶段，但“服务恢复”不等同于取证完成。对行业更重要的问题仍是攻击者如何操纵后台交易数据并触发签名授权，以及哪些控制未能在约3.875亿美元转出前阻断操作。
- **建议行动**：
  1. Bitget用户只根据平台内状态和官方公告操作，不点击所谓提前恢复、补偿申领或钱包验证链接。
  2. 机构客户在提款恢复后先进行小额验证，重新核对API密钥、地址白名单和账户会话。
  3. 同类交易平台应立即验证签名前交易数据的独立来源、金额上限、多方审批与异常地址阻断。
  4. 在完整根因报告和第三方取证结论发布前，不把“漏洞已修复”视为行业可复用的充分解释。
