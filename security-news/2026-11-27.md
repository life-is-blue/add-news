## 1. Hex.pm漏洞被实际利用，攻击者在六台包管理平台服务器执行命令

- **分类：** 软件供应链 / 包管理平台 / 数据泄露
- **严重度：** 严重
- **发布日期：** 2026-11-24（11月27日出现完整技术复盘，属72小时扩展）
- **可信度：** 官方确认
- **影响对象：** Elixir、Erlang、Gleam等生态使用的Hex.pm账户、私有包和依赖获取流程；直接使用相关底层库的应用也需检查。
- **事实摘要：** Hex团队确认，攻击者于11月23日利用CVE-2026-129514向hex.pm发送69个恶意请求，在六台Web服务器上实现操作系统命令执行。团队在约20分钟内拦截流量并部署修复，未发现包文件被修改、数据库写入异常或长期驻留。但由于数据库读取、环境变量读取和部分私有文档访问没有完整日志，无法排除邮箱、密码哈希、API密钥哈希、2FA秘密、会话、审计日志或私有内容被读取。Hex已轮换存储、CDN、邮件、数据库、会话及访问令牌相关凭据，并向瑞典监管机构、CISA和ENISA报告。
- **值得关注的原因：** 包管理平台是开发供应链的集中信任点。虽然现有证据没有显示恶意包替换，但服务器命令执行意味着攻击者理论上可访问签名、存储和账户数据。事件还暴露了同类不安全反序列化/伪造结构体问题，Ash 3.38.0和db_connection 2.10.3等组件已发布相关修复。
- **建议行动：**
  1. Hex.pm用户立即更换密码并重新设置2FA，保存新的恢复码；警惕以Hex安全事件为主题的钓鱼邮件。
  2. 重新登录Hex客户端，并在新注册表签名机制客户端发布后立即升级；过渡期只从repo.hex.pm获取包，不使用第三方镜像。
  3. 使用Ash的项目升级至3.38.0或更高版本，db_connection升级至2.10.3或更高版本，并检查flop最新修复。
  4. 私有包组织核对11月23日18:16—18:29 UTC前后的发布、下载、令牌和成员活动；如收到Hex单独通知，按潜在私有内容暴露处置。
  5. CI/CD中使用短期、最小权限的发布凭据，并对包内容、锁文件和构建产物执行独立完整性验证。
- **原始来源与补充来源：**
  - [Hex：Security incident on hex.pm](https://hex.pm/blog/security-incident-on-hexpm)
  - [SecurityWeek：Hex Package Manager Warns of Potential Data Breach](https://www.securityweek.com/hex-package-manager-warns-of-potential-data-breach/)

## 2. CISA将10项已利用漏洞加入KEV，覆盖通信、SD-WAN、虚拟化与制冷控制

- **分类：** 在野漏洞 / 关键基础设施 / 企业基础设施
- **严重度：** 严重
- **发布日期：** 2026-11-25
- **可信度：** CISA官方确认
- **影响对象：** Mitel MiCollab 10.3及更早版本的AWV组件、HPE Juniper Session Smart Conductor/Router、Danfoss AK-SM 800A系列，以及Vates Xen Orchestra。
- **事实摘要：** CISA基于实际利用证据向KEV加入10项漏洞：五项Mitel MiCollab漏洞，包括命令注入、XML注入、危险文件上传、弱认证与认证绕过；HPE Juniper Session Smart的CVE-2026-103406可让远程攻击者以root执行命令；Vates Xen Orchestra的CVE-2026-133469可通过构造令牌绕过认证并获得管理员能力；Danfoss AK-SM 800A的三项旧漏洞涉及路径遍历、命令执行和敏感信息暴露。多项漏洞的美国联邦处置期限为11月28日，并要求取证分诊。
- **值得关注的原因：** 这批KEV横跨统一通信、网络控制面、虚拟化管理和商业制冷控制。它们共同位于高权限或物理运营关键点，一次成功入侵可能扩大为凭据窃取、横向移动、虚拟机控制或制冷设备中断。旧CVE重新进入KEV也说明“已知多年”不等于“攻击价值降低”。
- **建议行动：**
  1. 立即盘点四类产品，按KEV及厂商通告升级或缓解；无法及时修复的公网系统应隔离或下线。
  2. Mitel用户限制AWV外部访问并应用MISA-2026-0012；检查异常文件上传、XML请求和命令执行迹象。
  3. Juniper用户升级至修复版本并审计Conductor/Router的root命令、异常salt minion ID及配置变更。
  4. Xen Orchestra用户检查异常认证令牌、管理员动作和已知攻击基础设施；Danfoss用户将AK-SM管理面从互联网和办公网隔离。
  5. 对CISA标记需取证的资产执行入侵检查，而非只确认版本号。
- **原始来源与补充来源：**
  - [CISA：Known Exploited Vulnerabilities Catalog](https://www.cisa.gov/known-exploited-vulnerabilities-catalog)
  - [The Hacker News：10 exploited vulnerabilities across Mitel, Juniper, Vates and Danfoss](https://thehackernews.com/2026/11/hackers-exploit-10-vulnerabilities.html)

## 3. GitLab修复MCP服务器OAuth令牌端点SSRF

- **分类：** MCP / 开发平台 / 服务端请求伪造
- **严重度：** 高
- **发布日期：** 2026-11-25
- **可信度：** 厂商官方补丁公告
- **影响对象：** 启用相关MCP服务器功能的GitLab EE实例；受影响版本以GitLab补丁公告列出的分支为准。
- **事实摘要：** GitLab在19.6.2、19.5.9、19.4.11、19.3.10、19.2.11、19.1.11、19.0.12和18.11.15等补丁版本中修复CVE-2026-135221。该问题源于MCP服务器OAuth处理对URL验证不足，在特定条件下，已认证用户可使GitLab服务器向内部网络资源发起请求。GitLab未在公告中声称该漏洞已在野利用。
- **值得关注的原因：** MCP服务通常位于AI工具、身份授权与企业资源之间。OAuth回调或令牌端点若能被用于SSRF，攻击者可能借受信任GitLab实例探测内网、云元数据或内部控制面；风险来自集成边界，而非模型本身。
- **建议行动：**
  1. 将GitLab升级至厂商列出的对应补丁版本或更高版本，并确认所有节点完成滚动升级。
  2. 检查MCP OAuth端点的异常目标URL、内网地址、云元数据地址和重复失败请求。
  3. 从网络层限制GitLab访问169.254.169.254、内部管理网段和无业务需要的服务，实施出站允许清单。
  4. 对MCP/OAuth集成使用最小权限、短期令牌和固定回调地址，记录授权、令牌交换及工具调用。
- **原始来源：**
  - [GitLab：Patch Release 19.6.2, 19.5.9, 19.4.11 and related versions](https://docs.gitlab.com/releases/patches/patch-release-gitlab-19-6-2-released/)

## 4. SAP确认GitHub相关安全事件，但源代码窃取和篡改主张尚未证实

- **分类：** 科技公司安全事件 / GitHub / 潜在源代码泄露
- **严重度：** 高（调查中）
- **发布日期：** 2026-11-27
- **可信度：** 安全事件由SAP确认；源代码泄露与修改仅属外部主张
- **影响对象：** SAP内部IT与GitHub相关开发环境；目前没有证据显示SAP客户业务数据或客户系统受到下游影响。
- **事实摘要：** SAP向Reuters和BleepingComputer确认其发现IT环境中的可疑活动，并已采取紧急措施保护客户和服务。SAP表示，根据当前调查，没有发现客户业务数据遭未授权访问，也没有证据显示客户系统被下游攻陷。媒体报道的攻击者声称包括盗取员工GitHub令牌、复制或修改源代码，但SAP尚未确认这些具体说法，也未公开受影响仓库、代码范围或恶意更改是否进入构建和发布流程。
- **值得关注的原因：** 即使客户数据未被直接访问，开发者身份或源代码环境失陷仍可能影响后续版本、补丁和供应链信任。但在官方取证结论之前，将攻击者的文件清单或篡改声明视为事实会放大未经证实的信息。
- **建议行动：**
  1. SAP客户关注官方安全通报和产品完整性指导，不根据攻击者宣传自行推断产品已被植入后门。
  2. 对近期下载的SAP补丁和软件使用官方渠道与签名校验，保留版本和哈希记录。
  3. 开发组织检查GitHub令牌范围、分支保护、工作流变更、发布审批和异常提交，特别是员工令牌能够触达CI/CD的路径。
  4. 若SAP后续确认特定产品或版本受影响，再按确切IoC和版本执行定向处置。
- **原始来源与补充来源：**
  - [Reuters：SAP flags security incident](https://www.reuters.com/technology/sap-flags-security-incident-says-no-evidence-unauthorized-access-customer-data-2026-11-27/)
  - [BleepingComputer：SAP confirms security incident after suspicious GitHub activity](https://www.bleepingcomputer.com/news/security/sap-confirms-security-incident-after-suspicious-github-activity/)

## 5. 美国空军Cloud One云平台被披露遭入侵，控制面风险仍在评估

- **分类：** 军事云平台 / 关键基础设施 / 重大网络入侵
- **严重度：** 严重
- **发布日期：** 2026-11-27
- **可信度：** Reuters多名知情人士披露；美国空军未确认具体网络状态
- **影响对象：** 美国空军Cloud One平台、运行于其上的人员、后勤、维护及部分指挥控制应用，以及相关云和承包商供应链。
- **事实摘要：** Reuters援引多名知情人士称，美国空军在近期升级工作中发现Cloud One平台遭入侵，导致部分应用迁移暂停、现有应用更新受阻，并撤销部分用户管理员权限。一名消息人士称攻击者利用软件漏洞进入控制面，但Reuters无法确认具体漏洞、攻击者身份、完整影响范围或数据是否被盗。美国空军仅表示不会评论特定网络的安全状态、漏洞或运行情况，并称持续采取保护措施。Cloud One整合Microsoft、Amazon、Oracle和Alphabet等云资源，承载多类人员、后勤和任务应用。
- **值得关注的原因：** 云控制面相当于跨应用和资源的高权限管理层，若被攻陷，潜在影响远大于单一工作负载。更新受阻还会造成次生风险，使平台在其他严重漏洞集中披露时无法及时修补。
- **建议行动：**
  1. 与Cloud One存在直接连接或供应关系的机构应审查联合身份、服务账户、管理API、软件部署和跨云日志，并等待正式通知。
  2. 军事和关键行业多云环境应将控制面身份与工作负载身份分离，强制抗钓鱼MFA、短期凭据和独立审批。
  3. 对被暂停更新的工作负载建立临时缓解、暴露面缩减和补丁积压清单，恢复后分批验证部署。
  4. 在官方细节公开前，不把匿名消息中的攻击入口、数据损失或国家归因当作已确认事实。
- **原始来源：**
  - [Reuters：Hackers breach US Air Force Cloud One computing platform](https://www.reuters.com/world/hackers-breach-us-air-force-flagship-cloud-one-computing-platform-2026-11-27/)

## 编辑说明

- Hex.pm没有发现包文件被修改，但数据库读取与部分私有内容访问缺少足够日志，因此“没有证据”不能写成“确认未读取”。

- GitLab MCP SSRF未被厂商标记为在野利用，严重度基于其内网访问能力和部署位置。
- SAP条目严格区分公司确认的可疑活动与攻击者尚未证实的源代码主张。
- Cloud One条目以Reuters交叉采访为基础，具体技术事实仍待美国空军或调查机构公开确认。
