## 1. WP Rocket未认证远程代码执行漏洞进入自动化攻击阶段

- **分类：** 在野漏洞 / WordPress插件 / 远程代码执行
- **严重度：** 严重
- **发布日期：** 2026-11-27
- **可信度：** 原始攻击遥测与CVE记录确认
- **影响对象：** WP Rocket 3.24.2之前版本，且启用了“CSS背景图LazyLoad”或“本地托管字体”任一功能的WordPress站点；两项功能默认关闭，但常见于性能优化配置。
- **事实摘要：** Patchstack确认CVE-2026-125812已被主动利用。该漏洞允许未认证攻击者向公开的`rocket_beacon`端点提交恶意URL，使站点从攻击者控制的服务器下载内容并保存为可执行PHP文件。首次攻击尝试出现在11月25日15:27 UTC，随后迅速转为自动化扫描；Patchstack称11月26日一天已拦截数万次请求，并观察到多个独立攻击集群。WP Rocket 3.24.2已修复该问题。
- **值得关注的原因：** 这是直接面向互联网、无需账号的代码执行，且WP Rocket拥有广泛部署基础。攻击者已从手工验证转向批量扫描；升级只能阻止新利用，不能删除此前写入的Webshell或持久化文件。
- **建议行动：**
  1. 将所有WP Rocket实例升级至3.24.2或更高版本，并逐站点确认实际生效版本。
  2. 无法立即升级时，同时关闭“CSS背景图LazyLoad”和“本地托管字体”，并应用可用WAF规则。
  3. 检查`rocket_beacon`异常请求、服务器访问陌生IP、`nip.io`或`trycloudflare.com`等临时域名的出站连接。
  4. 搜索`wp-content/wp-rocket-config/`、`wp-content/uploads/`及`wp-content/`中的异常PHP文件，尤其是`wp-media-*.php`。
  5. 若发现可疑文件，按站点已失陷处置：保全证据、轮换WordPress管理员、数据库、主机及API凭据，并从可信备份重建。
- **原始来源与补充来源：**
  - [Patchstack：Critical WP Rocket RCE Under Active Attack](https://patchstack.com/articles/critical-wp-rocket-rce-cve-2026-125812-under-active-attack/)
  - [Patchstack Database：CVE-2026-125812](https://patchstack.com/database/wordpress/plugin/wp-rocket/vulnerability/wordpress-wp-rocket-plugin-3-24-2-remote-code-execution-rce-vulnerability)

## 2. Drupal安装器访问绕过漏洞进入CISA KEV，已出现真实站点接管

- **分类：** 在野漏洞 / CMS / 站点接管
- **严重度：** 严重
- **发布日期：** 2026-11-27（CISA KEV更新；Drupal初始公告为11月25日）
- **可信度：** CISA、Drupal项目与多国响应机构官方确认
- **影响对象：** Drupal Core 10.6.23之前版本、11.0.0至11.3.23之前版本、11.4.0至11.4.14之前版本，且处于异常、不完整或安装器仍可访问状态的站点。
- **事实摘要：** CISA将CVE-2026-136716加入KEV。Drupal说明，先前SA-CORE-2026-017修复了多项安装器问题，但部分处于异常或不完整安装状态的站点仍可能通过`install.php`被绕过限制并接管，包括表面上正常运行的生产站点。项目明确表示漏洞正被在野利用；站点在被攻陷后可能不再呈现原始脆弱状态，因此只检查当前安装界面并不足以排除历史入侵。
- **值得关注的原因：** 此事件说明“已应用上一轮补丁”不等于风险关闭。漏洞状态可能由安装历史、配置和先前攻击改变，且被利用后攻击者可获得站点最高权限、修改内容、窃取数据并建立持久化。
- **建议行动：**
  1. 升级至Drupal 10.6.23、11.3.23、11.4.14或更高的受支持版本。
  2. 确认生产环境不暴露安装器，检查`sites/default/settings.php`、安装锁定状态及异常配置变化。
  3. 审查`install.php`访问、user 1账户变化、新管理员、模块启用、计划任务和可写目录中的PHP文件。
  4. 即使当前扫描显示“不再脆弱”，只要站点曾处于受影响状态，也应执行历史日志和完整性调查。
  5. 使用Drupal Steward推荐缓解的站点仍应尽快升级，以覆盖未来可能发现的其他攻击路径。
- **原始来源与补充来源：**
  - [Drupal：SA-CORE-2026-019](https://www.drupal.org/node/3641220)
  - [CISA：Known Exploited Vulnerabilities Catalog](https://www.cisa.gov/known-exploited-vulnerabilities-catalog)
  - [CERT-In：CIVN-2026-0579](https://www.cert-in.org.in/s2cMainServlet?VLCODE=CIVN-2026-0579&pageid=PUBVLNOTES01)

## 3. CISA确认两项GeoServer漏洞在野利用，可与其他问题串联为未认证RCE

- **分类：** 在野漏洞 / 地理信息基础设施 / 漏洞链
- **严重度：** 严重
- **发布日期：** 2026-11-27
- **可信度：** CISA及多国政府响应机构官方确认
- **影响对象：** GeoServer 2.27.7之前版本、2.28.6之前版本和3.0.2之前版本；相关GeoTools旧版本及启用了高风险扩展或服务的部署。
- **事实摘要：** CISA将CVE-2026-129243与CVE-2026-120705加入KEV。前者是授权检查绕过，未认证攻击者可通过带前缀的service参数调用本应受服务级角色保护的操作；后者涉及XML注入、外部实体和SSRF类风险。CISA指出，这些漏洞可与CVE-2026-129244、CVE-2026-129245和CVE-2026-129242等问题组合，实现对受影响GeoServer实例的未认证远程代码执行。政府通告确认两项漏洞正在被利用。
- **值得关注的原因：** GeoServer常暴露互联网并承载政府、城市规划、自然资源和关键设施的地理数据。单项漏洞的评分可能低于完整攻击链，但攻击者组合授权绕过、XML处理和命令执行后，可跨越认证边界并控制服务器。
- **建议行动：**
  1. 将GeoServer升级至3.0.2、2.28.6、2.27.7或更高的受支持版本，并同步更新容器镜像与GeoTools依赖。
  2. 盘点所有公网、测试和历史GeoServer实例，特别检查WPS、GeoFence、JDBC安全服务及不必要扩展。
  3. 审查异常service参数、XML请求、外部实体访问、SSRF目标、进程执行和GeoServer工作目录文件变化。
  4. 在无法立即升级时，将服务置于VPN或反向代理之后，仅允许可信来源，并禁用无业务需要的服务和扩展。
  5. 对已暴露的旧版本执行取证与凭据轮换，不把升级视为清除已有持久化。
- **原始来源与补充来源：**
  - [CISA：Known Exploited Vulnerabilities Catalog](https://www.cisa.gov/known-exploited-vulnerabilities-catalog)
  - [GeoServer：November 2026 Security Update](https://geoserver.org/vulnerability/2026/11/23/cve-update.html)
  - [加拿大网络安全中心：GeoServer security advisory AV26-1207](https://www.cyber.gc.ca/en/alerts-advisories/geoserver-security-advisory-av26-1207)
  - [GovCERT.HK：Multiple Vulnerabilities in GeoServer](https://www.govcert.gov.hk/en/alerts_detail.php?id=2220)

## 4. Traefik路径规范化漏洞可绕过认证或授权中间件

- **分类：** 云原生基础设施 / 反向代理 / 认证绕过
- **严重度：** 高
- **发布日期：** 2026-11-26
- **可信度：** GitHub安全公告与CVE记录确认；未见在野利用证据
- **影响对象：** Traefik 2.11.61及更早版本、3.x至3.7.17，以及3.8.0-rc.1；风险取决于路由、认证中间件与会剥离路径参数的后端是否组合出现。
- **事实摘要：** CVE-2026-137481源于Traefik默认启用的`sanitizePath`未正确处理带路径参数的点段，例如`/..;x/`。Traefik可能在未完全规范化的路径上匹配路由和应用认证/授权中间件，再把路径转发给会移除参数的后端，导致请求最终落到受保护资源。未认证攻击者可借此绕过前置身份控制。修复版本为2.11.62及3.7.18；3.8.0-rc.1也受影响。
- **值得关注的原因：** Traefik常作为Kubernetes和微服务的统一入口，组织可能把认证完全委托给其ForwardAuth或中间件。边缘代理与后端对路径解释不一致，会把“公开路由”和“管理路由”折叠为同一资源，形成系统性访问控制缺口。
- **建议行动：**
  1. 升级至Traefik 2.11.62、3.7.18或更高版本，避免使用受影响的3.8.0预发布版。
  2. 盘点共享后端的公开与受保护路由，检查是否依赖Traefik中间件作为唯一认证层。
  3. 在后端再次执行授权，不以反向代理已通过为唯一信任依据；统一代理与应用的路径规范化规则。
  4. 检索包含`..;`、编码点段、重复斜杠和异常路径参数的请求，并检查其是否命中管理或内部端点。
  5. 对无法升级的环境临时在WAF/入口层拒绝异常点段和路径参数组合，并验证不会产生编码绕过。
- **原始来源与补充来源：**
  - [Traefik GitHub Advisory：GHSA-cp28-5662-543f](https://github.com/traefik/traefik/security/advisories/GHSA-cp28-5662-543f)
  - [Red Hat：CVE-2026-137481](https://bugzilla.redhat.com/show_bug.cgi?id=CVE-2026-137481)
