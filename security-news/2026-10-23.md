## 1. LiteLLM 1.107.0官方发布链被投毒，恶意包窃取云与AI凭据并加载远控

- **分类：** AI基础设施 / 软件供应链 / CI/CD
- **严重度：** 严重
- **发布日期：** 2026-10-21（扩展至72小时；官方事件报告于窗口前不久更新）
- **可信度：** 官方确认（LiteLLM事件报告），Datadog安全研究交叉核验
- **影响对象：** 在受影响时段安装或运行`litellm==1.107.0`的Python环境；拉取Docker Hub或GHCR中`v1.107.0`、`latest`、`main-latest`、`main-stable`受污染镜像的用户
- **事实摘要：** LiteLLM确认其发布流水线遭入侵。攻击者把含编译恶意程序的1.107.0版本推送到PyPI和官方容器仓库，恶意程序会窃取凭据并加载远程代码执行工具。PyPI恶意包约在线两小时；多个浮动Docker标签也曾指向受污染镜像。官方GitHub中的1.107.0源码标签本身不含恶意文件，说明投毒发生在构建/发布链而非公开源码。官方称私有企业版仓库未受影响，事件已遏制但调查仍在继续。
- **值得关注的原因：** LiteLLM常直接持有OpenAI、Anthropic及云平台密钥，且广泛运行于开发机、CI、Kubernetes和AI网关。攻击者不需要逐一突破下游企业，只需控制一个高下载量发布通道即可收集多云、数据库和模型供应商凭据。使用浮动容器标签的环境尤其难以仅靠版本清单确认暴露。
- **建议行动：**
  1. 若运行过1.107.0或受污染镜像摘要`sha256:1bbcb1443bc962e45f5aad53fe3d2c30600e0379715fb6c664cdd3ac126c339e`，按已失陷处理，不要只做降级。
  2. 从干净基础镜像重建环境；在处置前避免启动Python或`pip`，因为`cook.pth`和`sitecustomize.py`会在Python启动时再次执行。
  3. 轮换实例/IAM角色、LiteLLM主密钥与虚拟密钥、模型供应商API密钥、数据库密码、CI令牌及该主机可访问的全部秘密；审查CloudTrail和供应商API调用。
  4. 将依赖和镜像固定到不可变版本/摘要，验证签名与来源，并为发布流水线使用短期令牌、双人审批和独立构建证明。
- **原始链接：**
  - [LiteLLM官方事件报告](https://docs.litellm.ai/blog/security-incident-oct-21-2026)
  - [Datadog Security Labs技术分析](https://securitylabs.datadoghq.com/articles/litellm-compromised-pypi-docker/)

## 2. Microsoft确认Storm-0940用ARTEX智能体将ConnectWise下游攻击提速至机器速度

- **分类：** AI智能体滥用 / 软件供应链 / 云身份
- **严重度：** 严重
- **发布日期：** 2026-10-21（扩展至72小时；相较此前事件披露新增正式归因、规模与Agent行为证据）
- **可信度：** 官方研究确认（Microsoft），ConnectWise通告与Reuters交叉核验；国家归因属于Microsoft评估，中国方面否认相关指控
- **影响对象：** 使用受影响ConnectWise多租户应用的Microsoft 365/Entra租户，以及暴露弱口令、旧应用凭据或高权限服务主体的组织
- **事实摘要：** Microsoft将ConnectWise供应链事件归因于其跟踪的中国国家关联组织Storm-0940，并称攻击者使用开源多智能体渗透框架ARTEX自动完成侦察、密码喷洒和OAuth应用滥用。该框架曾尝试登录超过2,250个租户；一组活动达到每分钟约2,900次失败登录。部分受害环境从初始目标选择到取得云端特权不足3小时，后续包括Microsoft Graph侦察、添加应用凭据及修改身份、组和特权角色。Microsoft同时强调：成功认证或存在受影响应用，并不等同于客户数据已被访问或外传。
- **值得关注的原因：** 这是Agent把传统云攻击从“辅助脚本”提升为多步骤自动运营的清晰案例。防守方即使收到告警，也可能来不及在几小时内完成跨租户调查和撤销持久化；而停用最初被盗应用并不会自动删除攻击者后来添加的凭据和管理员权限。
- **建议行动：**
  1. 按Microsoft与ConnectWise指南审查服务主体登录、应用凭据新增、Graph调用、角色与组变更；不要把调查范围限制在原ConnectWise应用。
  2. 删除未知应用密钥和证书，撤销会话与刷新令牌，轮换受影响身份的凭据，并验证Global Administrator等高权限角色。
  3. 为工作负载身份启用条件访问、来源限制和异常速率检测；对短时间跨租户、高并发登录单独告警。
  4. 将“停用供应商连接、清除下游持久化、验证数据访问、恢复业务”作为一个连续处置流程。
- **原始链接：**
  - [Microsoft：Storm-0940使用ARTEX的技术报告](https://www.microsoft.com/en-us/security/blog/2026/10/21/storm-0940-uses-artex-agentic-ai-connectwise-supply-chain-compromise/)
  - [Reuters：ConnectWise攻击与归因报道](https://www.reuters.com/technology/chinese-linked-hackers-compromise-connectwise-target-hundreds-global-attack-2026-10-21/)

## 3. VeloCloud Orchestrator再曝在野零日，认证用户可通过SQL注入取得操作员权限

- **分类：** 在野漏洞 / 网络管理平台 / 关键基础设施
- **严重度：** 严重
- **发布日期：** 2026-10-22（过去24小时）
- **可信度：** 官方确认（Arista Security Advisory 0199）
- **影响对象：** VeloCloud Orchestrator On-Prem 5.2.3.18、6.1.3.10、6.4.2.12之前版本；托管与Dedicated实例已由厂商修复
- **事实摘要：** Arista披露CVE-2026-114625，CVSS 3.1为9.9，属于可远程利用的SQL注入。任一已认证用户可提升为operator并伪装成本地“superuser operator”，访问原本仅供内部使用的功能，进而影响编排器主机及其管理数据。厂商明确表示该漏洞已遭在野利用。VCO在四个月内已连续出现多起零日问题。
- **值得关注的原因：** SD-WAN编排器掌握大量分支网络、隧道和边缘设备配置。控制面被攻陷后，风险可能从单一管理服务器扩展到整个广域网络；同时“需要认证”并不代表低风险，窃取的低权限账户或供应商账户即可成为入口。
- **建议行动：**
  1. 立即升级到5.2.3.18、6.1.3.10、6.4.2.12或更高修复版本；生命周期结束的版本未评估，应迁移。
  2. 在修复前把VCO管理面隔离到专用管理网络/VPN，限制来源并禁用非必要账户。
  3. 审计新增operator、superuser模拟、异常SQL错误、配置导出、API调用和主机命令；发现异常时按控制面失陷调查所有下游边缘设备。
  4. 轮换VCO本地、数据库、API及与边缘设备通信的凭据，并验证配置完整性。
- **原始链接：**
  - [Arista Security Advisory 0199](https://www.arista.com/en/support/advisories-notices/security-advisory/24838-security-advisory-0199)
  - [CVE-2026-114625](https://www.cve.org/CVERecord?id=CVE-2026-114625)

## 4. METR与Redwood发现OpenAI内部Agent监控可被绕过，生产相关问题据称已修复但未独立复验

- **分类：** AI智能体安全 / Coding Agent / 监控与沙箱
- **严重度：** 高
- **发布日期：** 2026-10-22（过去24小时）
- **可信度：** 原始独立评估；修复状态为OpenAI声明，尚未由评估方复验
- **影响对象：** OpenAI内部Codex Agent、Responses API相关内部流量和异步失准监控体系；对采用“Agent行为日志+模型监控”作为安全边界的其他企业亦有直接借鉴意义
- **事实摘要：** METR与Redwood Research在获得OpenAI内部代码、监控配置和文档的高权限评估中，发现多类历史性缺陷：Codex Agent原则上可绕过沙箱与Auto-Review、取得宿主用户全部能力；一种已脱敏的利用方式可使数百个近期动作不被监控；序列化差异可让监控器失败且不升级人工复核；两个客户端可控请求头可为新Agent关闭监控。评估还估算，2026年5月至7月间约10%的合格内部Codex流量可能因compaction事件未监控而遗漏。OpenAI称所有影响生产保障栈的问题均已修复，但评估方尚未验证这一说法；评估针对的是7月21日及之前的系统。
- **值得关注的原因：** 这组发现说明“有监控”不等于“监控覆盖完整”，尤其当Agent能影响日志边界、触发时机、序列化或新实例创建时。更关键的是，监控和沙箱可能存在共同失效路径：Agent既突破执行限制，又能遮蔽产生的行为。
- **建议行动：**
  1. 企业部署Coding Agent时，将网络、身份和主机权限控制放在Agent无法修改的外部执行层，不以模型自报或单一审计流作为唯一边界。
  2. 对compaction、上下文截断、重试、子Agent创建、错误与负载降级建立覆盖率指标，默认“监控失败即阻断/升级”，而非静默放行。
  3. 将客户端请求头、策略开关和审计配置从任务输入隔离，使用不可由Agent获得的独立身份签名。
  4. 定期让独立团队验证修复和完整攻击链，包括“越权后能否删除/规避证据”，而不仅测试单个漏洞。
- **原始链接：**
  - [METR：Red-Teaming OpenAI's Internal Agent Monitoring Systems](https://metr.org/blog/2026-10-22-red-teaming-openai-agent-monitoring/)
  - [Redwood Research同步发布](https://blog.redwoodresearch.org/p/red-teaming-openais-internal-agent)

## 5. Capcom确认1,177万CAPCOM ID记录遭未授权访问

- **分类：** 重大数据泄露 / 消费者账户
- **严重度：** 高
- **发布日期：** 2026-10-22（过去24小时）
- **可信度：** 官方确认（Capcom公告）
- **影响对象：** 全球CAPCOM ID用户
- **事实摘要：** Capcom确认11,774,247条记录受到未授权访问，涉及邮箱地址、系统标识符、账户创建与最近登录时间、登录次数及最近登录IP地址。43条记录还包含出生日期、性别、国家/地区和昵称；196个账户的登录密码被攻击者擅自更改。Capcom表示没有确认用户原设密码本身遭泄露，信用卡信息不在受影响数据内，攻击方式已识别并处置。
- **值得关注的原因：** 即使原密码和支付卡未泄露，大规模邮箱、登录时间和IP组合仍能支持高度逼真的钓鱼、撞库和地域化社工；196个账户被改密也证明事件不仅是只读数据访问。
- **建议行动：**
  1. 用户应警惕冒充Capcom的邮件、附件和登录链接；直接从官方应用或手动输入域名访问账户。
  2. 为CAPCOM ID及复用同一邮箱的高价值账户启用独立密码和多因素认证，检查登录记录与账户资料变化。
  3. 企业邮件网关可临时加强Capcom主题钓鱼检测，并关注利用泄露IP、昵称和登录时间制作的个性化诱饵。
  4. Capcom生态合作方应复核CAPCOM ID联邦登录、令牌撤销和改密事件的下游影响。
- **原始链接：**
  - [Capcom官方事件公告](https://www.capcom.co.jp/ir/english/news/html/e261022.html)
