## 1. CISA 将 MONAI Label 与 N-able Mail Assure 漏洞加入 KEV

- **分类：** 在野漏洞 / AI 基础设施 / 邮件安全平台
- **严重度：** 严重
- **发布日期：** 2026-11-23
- **可信度：** 官方确认
- **影响对象：**
  - Project MONAI Label 0.8.5 及更早版本（CVE-2026-133968）
  - N-able MailAssure / SpamExperts 早于 20261121.1943 的版本（CVE-2026-134624）
- **事实摘要：** CISA 基于实际利用证据将两项漏洞加入 Known Exploited Vulnerabilities（KEV）目录，并要求适用的美国联邦机构在11月26日前完成处置和取证。MONAI Label 漏洞允许未认证远程攻击者通过上传端点的路径遍历在服务进程可写位置创建任意文件，进而实现远程代码执行；AWS此前确认 Cairn 自主智能体在大学服务器攻击中发现并利用了该漏洞。项目现已发布 MONAI Label 0.8.6，同时修复数据存储上传和会话压缩包路径遍历。N-able 漏洞位于 LDAP 同步连接检查，具备高权限 API 账户的攻击者可让服务器连接任意内部主机和端口、判断其可达性并发送构造数据；N-able 已在 20261121.1943 修复。
- **值得关注的原因：** MONAI 事件的风险状态已从“源码已有修复、稳定包未发布”变为“正式修复包可用且进入 KEV”，修复和取证应立即并行。N-able MailAssure 位于邮件安全边界，SSRF 可把受信平台变成探测或访问内网服务的跳板。两项 KEV 均要求对可能被利用的资产进行取证，而非只升级版本。
- **建议行动：**
  1. MONAI Label 升级至 0.8.6，并同步更新实际运行的容器；不要只修改依赖文件。
  2. 对曾暴露到不可信网络的 MONAI 0.8.5 及更早实例，检查异常文件写入、`sitecustomize.py`、SSH/cron 项、训练 API 调用和对外连接。
  3. MailAssure/SpamExperts 确认版本至少为 20261121.1943，审计 LDAP 同步配置、异常内部地址、端口探测和 API 账户活动。
  4. 两类产品均应限制管理/API 网络可达性，轮换可能被进程访问的凭据，并保留日志进行事件调查。
- **原始来源与补充来源：**
  - [CISA：Known Exploited Vulnerabilities Catalog](https://www.cisa.gov/known-exploited-vulnerabilities-catalog)
  - [MONAI Label：0.8.6 Security Release](https://github.com/Project-MONAI/MONAILabel/releases/tag/0.8.6)
  - [MONAI Label：GHSA-qc22-rmgc-vg94](https://github.com/Project-MONAI/MONAILabel/security/advisories/GHSA-qc22-rmgc-vg94)
  - [N-able：CVE-2026-134624 Security Advisory](https://me.n-able.com/s/security-advisory/aArVy0000002mrlKAA/cve2026134624-mailassure-ldap-sync-connection-check-ssrf)
  - [AWS：Cairn AI agents found a zero-day](https://aws.amazon.com/blogs/security/chinese-nexus-actors-cairn-ai-agents-found-a-zero-day-on-their-own/)

## 2. Azure API Management Classic 漏洞被用于窃取客户 API 凭据并波及能源企业

- **分类：** 云平台 / 已利用漏洞 / API 供应链 / 关键基础设施
- **严重度：** 严重
- **发布日期：** 2026-11-23（挪威国家安全局更新）
- **可信度：** 官方确认（Microsoft 客户通知与挪威国家安全局）
- **影响对象：** 使用 Azure API Management Classic tier 的组织，尤其是在 APIM Named Values、策略或配置中直接保存 Token、密码和其他秘密的客户；挪威官方确认 Equinor 与 Skagerak Energi 在受影响机构之列。
- **事实摘要：** Microsoft 通过 Azure Service Health 通知客户，其11月18日发现 Azure API Management Classic 的安全问题，并于11月19日部署缓解。挪威国家安全局（NSM）确认，未知攻击者正主动获取 APIM 中的 Access Token、Secret 和 Named Value，影响跨越挪威多个行业及境外机构；Equinor 与 Skagerak Energi 属于已受影响组织。NSM 表示目前没有证据显示成功或尝试中的入侵影响了挪威机构的服务交付，但利用范围仍不确定。Microsoft 没有公开受影响客户总数、漏洞技术细节或攻击者身份。
- **值得关注的原因：** APIM 位于应用与后端服务之间，常保存调用数据库、SaaS、云服务和内部 API 的凭据。一旦这些秘密被读取，云平台漏洞可扩展为多个下游系统的访问。服务端漏洞已关闭不等于先前暴露的 Token 自动失效。
- **建议行动：**
  1. 所有 APIM Classic 客户按 NSM 指导将 Token、Secret 和 Named Value 视为可能外泄，立即轮换并检查其下游使用记录。
  2. 检查 APIM RuntimeVersion：0.52.x 应至少为 31936，0.53.x 应至少为 31938；低于门槛的实例联系 Microsoft。
  3. 盘点 APIM 后端连接、策略、Named Values 和 Credential Manager，确认每个秘密可访问的真实数据与服务范围。
  4. 将长期秘密迁移到 Azure Key Vault，通过 Managed Identity 和版本无关引用访问，避免把凭据直接嵌入策略。
  5. 从11月18日前后开始审查 Azure Activity、APIM、Key Vault、后端 API 和身份日志，发现异常时联系国家/行业响应机构。
- **原始来源与补充来源：**
  - [挪威国家安全局：Azure API Management 漏洞处置指导](https://nsm.no/fagomrader/digital-sikkerhet/digital-hendelseshandtering/varsler-fra-nsm/nsm-deler-tiltak-mot-sarbarhet-i-azure-api-management)
  - [Microsoft：Azure Service Health](https://portal.azure.com/#view/Microsoft_Azure_Health/AzureHealthBrowseBlade/~/serviceIssues)
  - [Microsoft Learn：Secure your Azure API Management deployment](https://learn.microsoft.com/azure/api-management/secure-api-management)
  - [BleepingComputer：Azure APIM flaw exploited to steal API credentials](https://www.bleepingcomputer.com/news/security/microsoft-azure-flaw-exploited-to-steal-customers-api-credentials/)

## 3. 原始研究：MCP 与 Agent Skills 攻击从“执行代码”转向“操纵指令”

- **分类：** MCP / Agent Skills / AI 软件供应链 / 原始安全研究
- **严重度：** 高（生态风险；不代表所有组件均受影响）
- **发布日期：** 2026-11-23
- **可信度：** 原始厂商研究；统计口径需谨慎解释
- **影响对象：** 从公共 npm、PyPI、MCP Server 或 Agent Skills 安装第三方组件，并允许 Agent 访问代码、文件、浏览器、云服务或企业数据的开发与生产环境。
- **事实摘要：** OX Security 表示其分析了2026年7月至10月间的542,207个 npm、PyPI、MCP Server 与 Agent Skill 组件。在被研究系统标记为可疑的 MCP Server 中，22%出现提示注入或工具投毒，16%存在安装/导入时执行；近三分之一无法识别明确所有者，83%的被标记 MCP Server 无法独立验证实际代码是否与声明一致。在179个被标记的 Agent Skills 小样本中，没有样本在安装时直接执行代码，但44%包含指示 Agent 向外部发送数据的内容。上述比例的分母是“被标记的可疑样本”，不是全部 MCP Server 或 Skill，不能解读为22%的整个生态均为恶意。
- **值得关注的原因：** 传统软件供应链检测主要寻找安装脚本、混淆代码或恶意二进制；MCP 与 Skill 可以只用自然语言指令，借用 Agent 已有的文件、网络和身份权限完成数据外传。即使仓库代码看似正常，远程 MCP 服务的实际行为也可能无法由本地代码审查证明。
- **建议行动：**
  1. 为 MCP/Skill 建立允许清单，记录发布者身份、源码、运行端点、权限、网络目的地和更新渠道。
  2. 默认不给第三方工具读取主目录、环境变量、密钥库和跨仓库权限；按任务发放短期、最小权限凭据。
  3. 检查工具描述、Skill 指令和返回内容中的隐蔽数据外传要求，对上传文件、发送凭据和访问外部域名设置策略拦截。
  4. 将远程 MCP 服务视为外部 SaaS，而非普通依赖：要求身份验证、日志、固定端点、变更通知和数据处理协议。
  5. 对研究统计保持审慎，优先依据本组织安装清单、行为日志和可复现样本制定处置优先级。
- **原始来源：**
  - [OX Security：Plug and Pray — How AI Is Changing Software Supply Chain Attacks](https://www.ox.security/reports/plug-and-pray-how-ai-is-changing-software-supply-chain-attacks/)
  - [OX Security：研究摘要与方法说明](https://www.prnewswire.com/news-releases/ai-agents-are-taking-orders-from-strangers-ox-security-research-finds-302948335.html)
