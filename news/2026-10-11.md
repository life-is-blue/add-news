## 2. RucTangle：把编码智能体的大补丁拆成每一步都可运行的提交

![RucTangle 论文页面](https://image.thum.io/get/width/1200/crop/675/noanimate/https://arxiv.org/abs/2610.11593)

*图片来源：[arXiv 论文页面](https://arxiv.org/abs/2610.11593)*

- **时间范围：**扩展至过去 72 小时
- **发布日期：**2026-10-09（arXiv 当日公开列表；v1 提交于 2026-10-08 09:42 UTC）
- **事实摘要：**RucTangle 面向编码智能体常见的“大而混杂”补丁，把不同开发目的拆成有序提交，并要求每个中间提交都保持项目可运行。作者在 131 个智能体生成补丁上比较四种基线，RucTangle 生成的历史全部可运行，而基线有 20.6%–37.4% 的提交历史不可运行。进一步在 453 个引入回归的补丁上测试时，把这种提交历史加入上下文使另外两个修复智能体的 pass@1 绝对提升 5.2 个百分点。
- **为什么值得关注：**它把人类工程中的“小步、可运行提交”转化为智能体可消费的验证结构；这不仅改善代码评审，也让后续代理能沿历史定位回归，而不是只面对一个难以解释的最终 diff。
- **原文链接：**[Runnable Commit Untangling for Coding Agents](https://arxiv.org/abs/2610.11593)

## 3. Skill Constellations：首次绘制智能体技能复制网络，发现安全修复几乎不会自动传播

![Skill Constellations 论文页面](https://image.thum.io/get/width/1200/crop/675/noanimate/https://arxiv.org/abs/2610.11169)

*图片来源：[arXiv 论文页面](https://arxiv.org/abs/2610.11169)*

- **时间范围：**扩展至过去 72 小时
- **发布日期：**2026-10-09（arXiv 当日公开列表；v1 提交于 2026-10-08 03:25 UTC）
- **事实摘要：**研究者从 GitSkills 中每个 `skill.md` 的 Git 历史构建首个带时间信息的技能复制网络，覆盖 GitHub 上 2,193,119 次技能采用。结果显示，少量仓库是绝大多数复制的源头，但 stars 无法识别这些关键源；复制后的技能也几乎不再跟随上游变化，因此源头修复很少抵达下游。其传播模型选出的前 100 个审计目标可覆盖后来 14.9% 的高风险技能采用，而审计 stars 最高的 100 个仓库仅覆盖 0.5%。
- **为什么值得关注：**Claude Code、Codex 等工具会以用户权限运行技能中的指令与脚本；当生态依赖复制粘贴而非版本化引用时，它已成为缺少来源、版本和补丁传播机制的软件供应链。
- **原文链接：**[Skill Constellations](https://arxiv.org/abs/2610.11169) · [项目网站](https://fahdseddik.github.io/skill-constellations/)

## 4. AI 生成 PR 的隐性成本：239 名开发者认为关键不是“是否由 AI 写”，而是谁承担验证与维护

![AI-authored Pull Requests 研究页面](https://image.thum.io/get/width/1200/crop/675/noanimate/https://arxiv.org/abs/2610.11179)

*图片来源：[arXiv 论文页面](https://arxiv.org/abs/2610.11179)*

- **时间范围：**扩展至过去 72 小时
- **发布日期：**2026-10-09（arXiv 当日公开列表；v1 提交于 2026-10-08 03:38 UTC）
- **事实摘要：**这项混合方法问卷覆盖 31 个国家、239 名具有代码评审经验的从业者，研究他们如何处理 AI 生成的 pull request。受访者并未把“AI 作者”本身当作一票否决条件，而是关注范围是否受控、理由是否扎根项目、是否有 CI 之外的验证、贡献者是否回应，以及合并后是否有人负责。作者把缺失理由、验证和所有权所转嫁给评审者的额外劳动称为“reviewability debt（可评审性债务）”。
- **为什么值得关注：**自主开发的瓶颈正在从生成代码转向人类评审吞吐量；若平台只优化提交速度而不要求可验证证据和明确所有权，智能体越高产，维护者负担反而越大。
- **原文链接：**[Who Pays the Review Cost?](https://arxiv.org/abs/2610.11179)

## 5. 嵌入式编码智能体迎来闭环评测：420 次运行同时检验构建、执行反馈与修复迭代

![嵌入式编码智能体闭环评测论文页面](https://image.thum.io/get/width/1200/crop/675/noanimate/https://arxiv.org/abs/2610.11447)

*图片来源：[arXiv 论文页面](https://arxiv.org/abs/2610.11447)*

- **时间范围：**扩展至过去 72 小时
- **发布日期：**2026-10-09（arXiv 当日公开列表；v1 提交于 2026-10-08 08:02 UTC）
- **事实摘要：**该基准要求智能体把自然语言工程需求转成模拟 ESP32 固件，在受限工作区中构建、运行、自验并迭代，而不是只做一次性代码生成。套件包含 5 个嵌入式控制任务与 4 种反馈场景，研究评估 7 组 GPT 与 Qwen 配置、每种条件重复 3 次，共 420 次运行。论文报告 gpt-5.4 在所测配置中通过率最高但未饱和基准，qwen3.5-27B 是表现最强的本地模型，小模型在通过率与搜索效率上明显下降。
- **为什么值得关注：**当智能体进入固件、机器人和边缘设备开发，静态代码正确并不足够；闭环行为、时序和安全约束必须通过可重放执行环境验证，这类基准更接近真实工程风险。
- **原文链接：**[Closed-loop evaluation of LLM agents for embedded software development](https://arxiv.org/abs/2610.11447) · [期刊 DOI](https://doi.org/10.1016/j.sysarc.2026.103937)
