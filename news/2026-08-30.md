## 1. SWE-Prime：只用 10% 高质量轨迹，代码智能体训练反而更强

![SWE-Prime 论文页面](https://image.thum.io/get/width/1200/crop/675/noanimate/https://arxiv.org/abs/2608.27449)

*图片来源：[arXiv 论文页面](https://arxiv.org/abs/2608.27449)*

**扩展窗口｜发布日期：2026-08-27（UTC）**

SWE-Prime 不把“成功解决任务”直接等同于优质训练数据，而是先按过程质量、结果质量和代表性筛选完整轨迹，再在语义片段层面选择真正有贡献、可学习且风险较低的步骤。作者保留完整上下文、只让选中片段参与损失计算；在 SWE-Bench Pro 与 SWE-Bench Verified 上，用筛出的 10% 轨迹训练，分别相对全量已解决数据最高提升 12.2% 和 24.2%。

**为什么值得关注：** 自主编程的瓶颈正从“收集更多轨迹”转向“筛掉成功轨迹里的冗余和坏习惯”；这对降低训练成本、避免模型模仿危险操作都有直接意义。

**原文：** [SWE-Prime: Fewer Trajectories, Better Performance](https://arxiv.org/abs/2608.27449)

## 2. MCR-Bench：把代码审查从单轮判断推进到真实多轮缺陷追踪

![MCR-Bench 论文页面](https://image.thum.io/get/width/1200/crop/675/noanimate/https://arxiv.org/abs/2608.27442)

*图片来源：[arXiv 论文页面](https://arxiv.org/abs/2608.27442)*

**扩展窗口｜发布日期：2026-08-27（UTC）**

MCR-Bench 收录 2,269 个真实世界多轮代码审查任务，覆盖 5 种常用编程语言，并为缺陷描述、类型、严重程度及跨轮状态变化提供细粒度标注。论文报告主流模型在缺陷检测和生命周期追踪上仍明显受限，交互轮数增加时性能显著下降；复杂语义、低显著性缺陷，以及跨轮时间错位和长期记忆不足是主要失败来源。该工作已被 ISSTA 2026 接收。

**为什么值得关注：** 生产级审查不是一次性“看 diff”，而是评论、修复、再审查的协作过程；这个基准更接近 Copilot、Codex 或 Claude Code 真正进入 PR 工作流后需要面对的状态管理问题。

**原文：** [From Static to Dynamic: Benchmarking Real-World Code Review with MCR-Bench](https://arxiv.org/abs/2608.27442)

## 3. WikiSkill：用持久知识库让智能体经验真正沉淀为可迁移技能

![WikiSkill 论文页面](https://image.thum.io/get/width/1200/crop/675/noanimate/https://arxiv.org/abs/2608.27454)

*图片来源：[arXiv 论文页面](https://arxiv.org/abs/2608.27454)*

**扩展窗口｜发布日期：2026-08-27（UTC）**

WikiSkill 将原始执行经验、长期积累的知识和可执行技能拆成三层，并用持续更新的 wiki 支撑后续技能演化。作者在多种基准与模型上报告其整体优于既有技能演化方法，并发现技能可跨模型家族迁移；部分情况下，小模型配合演化技能还能超过明显更大的无技能模型。消融实验显示，持久知识积累是性能提升的关键组成。

**为什么值得关注：** 这为团队级自主开发提出了比“无限追加聊天历史”更可扩展的路径：把项目经验整理成可审计、可复用、可跨智能体共享的知识与技能资产。

**原文：** [WikiSkill: Compiling Agent Experience into Persistent Knowledge for Skill Evolution](https://arxiv.org/abs/2608.27454)

## 4. ASIL：结构化状态与语义动作显著胜过“截图再点击”

![ASIL 论文页面](https://image.thum.io/get/width/1200/crop/675/noanimate/https://arxiv.org/abs/2608.26991)

*图片来源：[arXiv 论文页面](https://arxiv.org/abs/2608.26991)*

**扩展窗口｜发布日期：2026-08-27（UTC）**

ASIL 为软件操作智能体提供结构化 JSON 状态和可由代码执行的语义动作，并在 15 个应用、300 个单应用任务和 80 个跨应用任务上评测。论文报告闭源模型在 ASIL 上严格成功率超过 80%，平均每项少于 5 个动作；相同任务在修复后的截图点击运行时、50 步预算下只有 6.6% 与 26.6%。小规模监督微调还把 Qwen3.5-2B 从 58.0 提升到 72.1、9B 从 66.6 提升到 80.4；该工作已被 EMNLP 2026 Findings 接收。

**为什么值得关注：** 对跨 IDE、浏览器和办公软件的开发协作代理来说，标准化、结构化接口可能比单纯升级视觉模型更能提升可靠性，也更容易做权限控制与审计。

**原文：** [ASIL: Replacing Screenshot-and-Click with Structured State and Semantic Actions](https://arxiv.org/abs/2608.26991)

## 5. FaulT-Bench：Claude Code 等代理会把“其实没故障”诊断成故障

![FaulT-Bench 论文页面](https://image.thum.io/get/width/1200/crop/675/noanimate/https://arxiv.org/abs/2608.27021)

*图片来源：[arXiv 论文页面](https://arxiv.org/abs/2608.27021)*

**扩展窗口｜发布日期：2026-08-27（UTC）**

FaulT-Bench 构建 200 个网络排障场景，覆盖 8 种拓扑，包括真实故障、错误设备归因、错误根因以及网络健康但工单声称有故障的情况。对 SADE、ReAct 和 Claude Code 的评测显示，三者在准确工单上接近饱和、也能抵抗部分误导，但面对错误工单时会显著退化，往往持续探查直至把正常现象解释成根因；工单是否含足够可验证细节，比报告者是否自信更影响表现。

**为什么值得关注：** 自主运维和开发代理需要会得出“无需修复”的结论；否则错误告警会被智能体放大成无谓修改、停机或成本，这也是从演示走向生产必须解决的校准问题。

**原文：** [FaulT-Bench: Towards Benchmarking Network Troubleshooting LLM Agents under Unreliable User Tickets](https://arxiv.org/abs/2608.27021)
