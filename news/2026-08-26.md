## 1. Pufibara：同模型下，智能体“脚手架”本身也能显著改变工程结果

![Pufibara 论文页面](https://image.thum.io/get/width/1200/crop/675/noanimate/https://arxiv.org/abs/2608.23653)

*图片来源：[arXiv 论文页面](https://arxiv.org/abs/2608.23653)*

**扩展窗口｜首次提交：2026-08-24（UTC）**

研究提出面向 Modelica 物理系统建模的 Pufibara 智能体框架：跨修订保存工程状态，把仿真证据绑定到产生它的候选版本，并将“提交”设为显式动作。作者还构建了 232 项任务的 Modelica Agent Workflow Benchmark；在匹配相同模型后，Pufibara 使用 DeepSeek v4 Flash 和 Claude Sonnet 5 均通过 202 项，Claude Code 分别通过 185 和 187 项。论文同时报告 Pufibara 的逻辑 token 总量低 76.4%–82.5%，顺序运行时间低 6.1%–58.4%。

**为什么值得关注：** 这项结果把智能体竞争从“底层模型谁更强”推进到状态管理、证据溯源和提交协议等系统设计；它也提醒团队，代码智能体评测应比较完整工作流，而不只是模型或单次生成。

**原文：** [Beyond Executable Models: The Pufibara Agent Harness and the Modelica Agent Workflow Benchmark](https://arxiv.org/abs/2608.23653)

## 2. 失败反馈可能适得其反：小模型智能体更容易复现刚刚失败的调用

![Feedback That Backfires 论文页面](https://image.thum.io/get/width/1200/crop/675/noanimate/https://arxiv.org/abs/2608.23651)

*图片来源：[arXiv 论文页面](https://arxiv.org/abs/2608.23651)*

**扩展窗口｜首次提交：2026-08-24（UTC）**

研究在模拟工具调用与 MBPP 代码修复中测试 6 个、横跨 4 个家族的 1.35 亿至 17 亿参数指令模型。把失败调用原样留在上下文后，重复该调用的概率从 0.06 升至 0.54；反事实实验显示，失败调用的表面形式解释了 83% 的负面影响。作者报告，将原始调用改写成运行时生成的失败描述可消除 76% 的“反向纠错”，而仅增加“不要重复”指令并未奏效。

**为什么值得关注：** 许多代码智能体会把工具错误、测试失败或命令输出原样追加到轨迹中；这项研究表明，失败记录的表示方式可能直接制造循环重试，尤其影响本地小模型与低成本代理。

**原文：** [Feedback That Backfires: Why Small Language Model Agents Repeat the Call They Just Watched Fail](https://arxiv.org/abs/2608.23651)

## 3. CloudEmu：用神经符号代码合成自动构建云服务模拟器

![CloudEmu 论文页面](https://image.thum.io/get/width/1200/crop/675/noanimate/https://arxiv.org/abs/2608.23842)

*图片来源：[arXiv 论文页面](https://arxiv.org/abs/2608.23842)*

**扩展窗口｜首次提交：2026-08-24（UTC）**

CloudEmu 从云服务文档自动合成 API 级模拟器，把大模型的文档理解与代码生成能力，同用于约束精度的云领域符号抽象结合起来。系统还把真实云环境作为测试、修复和对齐的“裁判”；作者在 AWS 与 GCP 服务上评估后，报告其覆盖率和准确率超过长期人工开发的 LocalStack。论文目前仍处于评审阶段，摘要未给出足以独立核验“超过”幅度的完整数字。

**为什么值得关注：** 若结果能够复现，DevOps 智能体可在本地、更安全且成本更低地测试 CLI、API 与基础设施即代码，同时让模拟器跟随快速变化的云 API 自动演进。

**原文：** [Automated Synthesis of Cloud Emulators](https://arxiv.org/abs/2608.23842)

## 4. ToolRobustBench：把工具调用失败拆解到接口、意图、输出和运行环境

![ToolRobustBench 论文页面](https://image.thum.io/get/width/1200/crop/675/noanimate/https://arxiv.org/abs/2608.23635)

*图片来源：[arXiv 论文页面](https://arxiv.org/abs/2608.23635)*

**扩展窗口｜首次提交：2026-08-23（UTC）**

ToolRobustBench 不再只看端到端成功率，而是沿工具选择、模式理解、参数绑定、结果解释和任务完成逐阶段诊断。基准包含 15,456 个单类扰动实例，覆盖 7 个模型、16 个本地工具、4 类扰动及 14 个子类型；作者发现工具输出/观察扰动是最主要瓶颈。混合扰动还呈现非加性的失败模式，无法由各单类测试简单推算。

**为什么值得关注：** 这为 GitHub、Slack 或终端驱动的自主开发代理提供了更接近生产环境的评测思路：真实故障往往来自脏输出、环境变化和多阶段错误传播，而不是理想化工具定义下的单次调用。

**原文：** [ToolRobustBench: Stage-Wise Perturbation Evaluation and Failure Diagnosis for Tool-Calling Agents](https://arxiv.org/abs/2608.23635)

## 5. FPGAgent：多智能体把 HLS 代码验证推进到真实 FPGA 板级执行

![FPGAgent 论文页面](https://image.thum.io/get/width/1200/crop/675/noanimate/https://arxiv.org/abs/2608.23630)

*图片来源：[arXiv 论文页面](https://arxiv.org/abs/2608.23630)*

**扩展窗口｜首次提交：2026-08-23（UTC）**

FPGAgent 面向从自然语言规格到可执行高层综合（HLS）设计的完整链路，通过领域知识注入和演化搜索生成内核，再自动编写 C++ 验证程序、诊断修复，并生成主机端代码完成真实 FPGA 编译与板级运行。作者在包含 78 个任务的 HLS-Eval 上使用 5 个模型评估，报告相较现有基线平均提升 16.9% 的可综合率、26.7% 的可执行率与 30.6% 的功能正确率。

**为什么值得关注：** 它把“代码能生成”与“硬件上真正能运行”区分开来，展示了多智能体、自动验证和真实执行反馈如何进入高成本、高约束的工程开发环节。

**原文：** [FPGAgent: An LLM-Assisted Framework for Autonomous HLS Code Generation and Verification in FPGA Environments](https://arxiv.org/abs/2608.23630)
